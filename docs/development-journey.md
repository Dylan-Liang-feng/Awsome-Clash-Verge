# 从一句话到一条可核对的分流规则

项目起点是规则编辑器里的一个实际操作难题：用户知道自己想让哪个软件或网站直连，却经常不知道进程名、官网域名和 Mihomo 匹配类型。沿用上游的订阅、规则优先级和保存流程后，新增功能只需负责把一句需求转换成用户能检查的前置规则。

| 阶段 | 遇到的问题 | 最终采用的做法 |
| --- | --- | --- |
| 本地模型原型 | 小型量化模型能处理简单句。在一条包含多个目标和不同出站方向的指令中，曾把方向分配反了 | 改用可配置的 Chat Completions API。一次提交整句，要求模型逐项返回目标、范围和出站方向。发行包无需下载模型权重 |
| 桌面程序匹配 | 用户说的是软件俗称，安装位置、可执行文件名和辅助进程随版本变化 | 用安装记录、快捷方式、进程及文件产品信息核对模型建议的别名。有多个可信安装位置时让用户选择；共享 Node 运行时需要结合接口域名缩小范围 |
| 网站范围判断 | 把结构化结果转回中文再用关键词解析，换一种表达就可能丢掉子域范围。直接从产品主机向上截断也可能涵盖整家平台 | 保留结构化意图，先查 Wikidata、ROR 或产品的公开页面，再把证据交给模型复核。客户端检查后缀边界和规则是否可表达。入口域名和可选资源域名分别展示 |
| 保存与验证 | 生成成功只说明有了一组候选。共享 CDN、多个同名程序、旧连接都会干扰判断 | 保留预览、逐项选择和取消。保存后以新连接核对命中规则和实际出站。在域名检索中同时检验查不到、重名、公共后缀等情形 |
| 完全绕过 TUN | 即使 Mihomo 命中了 DIRECT，浏览器连接仍可能先进入 TUN | 专用 PAC 将匹配网站交给回环 HTTP 入口，出口绑定当前物理网卡并使用对应 DNS。其余浏览器连接沿系统路由进入 TUN。网卡切换后重新激活订阅 |

## 两个容易误判的例子

对「QQ 邮箱网页直连」，检查官方邮件入口和页面实际引用的专用主机；只因服务同属一个平台而扩大到整个平台，会影响与邮箱无关的连接。「某大学官网和所有子域名」的范围更宽，需要先找到属于该机构的官网，然后才有依据使用域名后缀规则。第三方登录、支付或共享 CDN 仍可能使用独立域名。

对「这个网站绕过 TUN」，仅看网页能否打开不足以验收。开发中的 Windows 实机对照在同一浏览器发起两组新请求：目标网站返回 HTTP 200，并能关联浏览器到回环入口、物理网卡到远端的连接；对照网站仍显示 TUN 入站和代理出站。这个结果覆盖遵循系统 PAC 的浏览器及当时的网卡环境。其他进程、自带代理的浏览器、不同协议和网络切换后的结果要分别验证。

## 复核方式

- 在仓库根目录运行 `corepack pnpm exec vitest run`。公开源码快照通过 17 个测试文件、64 项测试，覆盖复合指令、实体与域名范围、部分进程匹配和 TUN 绕行规则等。测试使用构造的数据，不能据此估算任一在线模型的识别准确率。
- 针对新接口，先用一条包含不同出站的请求，核对每项所选策略。对新网站再测试「仅官网」「官网和子域名」「相关资源」三种表达，检查预览中哪些域名发生变化。
- 打包时从干净源码构建并逐项选择发布文件。运行目录可能同时包含订阅、节点凭据和调试副本；即使只复制可执行文件，调试信息和编译器错误定位字符串也可能包含开发者路径。检查范围因此涵盖 Git 快照、前端产物和最终二进制。
